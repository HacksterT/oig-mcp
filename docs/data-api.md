# OIG Data API contract

This server reads all of its data from one HTTP API, built and hosted by the `oig-data-source` repository (a Python API over a SQLite database, run in a container on Troy's Mac and exposed through Cloudflare Tunnel with Access service tokens). This file records what the MCP server expects from that API. The endpoints below are implemented in `oig-data-source`, not here.

The API is deliberately generic: filter, paginate, and aggregate over reports, recommendations, facilities, clusters, and facility responses. The MCP tools compose these calls into goal-level answers. An endpoint that mirrors one tool is a sign that logic has leaked from the server into the API.

## Conventions

- Base URL: `OIG_DATA_API_BASE_URL`, for example `http://127.0.0.1:8787/v1/` with the oig-data-source container running (`docker compose up -d`).
- Auth: `CF-Access-Client-Id` and `CF-Access-Client-Secret` headers when hosted, plus `Authorization: Bearer <OIG_DATA_API_KEY>` when the API sets `OIG_API_KEY` (a missing or wrong key is 401). Only `/health` is open; `/health/search` needs the key. None locally.
- Tracing: within a tool call, the MCP server sends `X-Trace-Id`, `X-OIG-Client`, and `X-OIG-Tool`. The API ignores them unless its test traces are on, and then records them so each request can be matched to its tool call.
- All responses are JSON, with `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. Lists use the envelope `{total, count, offset, items, has_more, next_offset}`.
- Every response includes `data_as_of` (YYYY-MM-DD).
- Reports are keyed by `node_id` (the vaoig.gov Drupal node id); recommendations by `rec_id` = `<node_id>-<rec_no>`. vaoig.gov exposes a node id only for reports that have recommendations (about half of all reports; oig-data-source ADR-04), so report list items also carry `path`, and `node_id` may be null there.
- Status values: `open`, `closed-implemented`, `closed-not-implemented`.

## Endpoints

| Method and path | Returns | Used by |
|---|---|---|
| `GET meta` | `data_as_of`, `counts`, `reconciliation` (database open counts versus the OIG dashboard), migration and parser versions | `vaoig_get_dataset_status` (implemented) |
| `GET search` | **The one search call.** A question in any wording; keyword and semantic results fused into one ranked list, plus PDF page hits | search findings, peer corrective actions |
| `GET recommendations` | Recommendations filtered by `q` (FTS5), `status`, `action_office`, `topic`, `report_type`, `visn`, `state`, `published_from`, `published_to`; paginated | search support, `vaoig_analyze_recommendations` filters |
| `GET reports` | Reports filtered by `q` (title), `report_type`, `topic`, `visn`, `state`, dates, `report_number`, `path`, `has_recommendations`; paginated; reaches reports with no node id | report lookup |
| `GET reports/{node_id}` | One report with all recommendations, closure dates, facility responses, standards cited, PDF URL | report detail |
| `GET pages/search` | PDF page hits for `q` with `node_id`, `page_no`, snippet | narrative search |
| `GET facilities` and `GET facilities/{station_number}` | Facility registry; one facility's reports, inspections, and recommendations | facility profile, inspection readiness |
| `GET inspections` | Inspections by facility, program, and date, with the next-window estimate | inspection readiness |
| `GET clusters` and `GET clusters/{cluster_id}` | Templated recommendation clusters with member reports and statuses | systemic clusters |
| `GET metrics/closure` | Median and interquartile days to closure and not-implemented rate, grouped by `office`, `topic`, or `report_type` | `vaoig_analyze_recommendations` |
| `GET metrics/counts` | Report and recommendation counts by year for a filter set | `vaoig_analyze_recommendations` |
| `GET taxonomy/{facet}` | OIG facet values (topics, offices, states, VISNs) | resources |

## One search tool

Expose one search tool to the assistant, backed by `GET search`, with no mode or strategy parameter. Several similar search tools make an assistant guess between them, and the pipeline already runs every method on every query. `GET recommendations`, `pages/search`, and the metrics endpoints are for exact listing and counting inside other tools, not for separate search tools.

Use `GET search` to find; use `GET recommendations` and `metrics/*` to count. A search result is a ranked shortlist with no natural end, so its `total` is never a count of findings.

## Tool surface

Two decisions from Troy (2026-11-04) keep the tool list short:

- **One analysis tool.** Merge the planned `vaoig_get_theme_trend` and `vaoig_get_closure_performance` into one tool that filters a set and groups it by year, office, topic, or report type. Both are the same shape, and two of them would make an assistant guess. It calls `metrics/counts` and `metrics/closure`.
- **New facts belong in existing tools.** Repeat findings, how common a finding is, how long it takes to close, and promised versus actual dates are fields below, not new tools.

Lead with what OIG's site cannot do: facilities' committed corrective actions, cross-report recurrence, trends, and time to close. OIG already offers solid keyword search and filters, so do not compete there.

## Implemented

Every endpoint above is live as of 2026-11-04. The API's own OpenAPI document is at `/openapi.json` and interactive docs at `/docs`.

**Unknown parameters.** Any query parameter an endpoint does not declare returns 422, with the name in `detail[].loc` and the allowed names in `detail[].msg`, so a misspelled filter cannot return unfiltered numbers. Check `/openapi.json` before sending a new one.

**Shared parameters.** `limit` (1 to 100, default 20) and `offset` (0 or more). An invalid value returns 422 with the parameter named in `detail[].loc`. `q` is full-text search (SQLite FTS5, porter stemming, BM25 ranking). With the default `q_mode=terms`, each word is quoted and all must match, so stray quotes or operators in user text are harmless, but a whole sentence usually finds nothing. `q_mode=any` matches any meaningful word. `q_mode=raw` passes FTS5 syntax through (`OR`, `NEAR`, phrases, prefix `*`). Limits on `q` are under Query limits below. Report filters are `report_type` (slug or label, for example `audit` or `Healthcare Facility Inspection`), `topic`, `visn`, `state` (label, case-insensitive, or the site's term id), `published_from` and `published_to` (YYYY-MM-DD, inclusive), `report_number`, `station_number`, and `exclude_station_number` (to see only a facility's peers).

**VISN numbering** (oig-data-source `docs/schema.md`, "VISN numbering"). The `visn` filter matches OIG's tags on each report, and a report can carry several. VA replaced its 18 VISNs with five on July 15, 2026. OIG tags reports from August 5, 2026 with the new labels (1 to 5) and did not retag older ones, so labels 1, 2, 4, and 5 each name two regions and one label cannot tell them apart; 3 is new only. `visn=17` returns nothing after July 2026. Facility `visn` values are mostly the old numbering, with a few new and a few wrong. The tools add a notice whenever a VISN filter is used and on every facility result, and the filter description says to use state to follow a region across the change.

**Query limits** (oig-data-source #26, #34, #35; live 2026-11-10). These bound what one query can cost.

| Condition | Response |
|---|---|
| `q` over 512 characters on `search`, `pages/search`, `recommendations`, `reports`, or `metrics/*` | 422 |
| `q_mode=terms` with more than 32 words | 400, "q has more than 32 words; use q_mode=any for long text" |
| `q_mode=any`, and `search` in every case, past 32 meaningful words | The extra keywords are ignored. `search` still embeds the whole question. |
| `q_mode=raw` with a prefix shorter than 3 characters before `*`, a `NEAR` group of more than 8 terms, or any syntax error, including `col:term` | 400, "Invalid search query" |
| A full-text query running past 2 seconds | 503, "Search timed out" |
| More than 4 `search` or `pages/search` calls at once | Extra calls wait up to 10 seconds, then get 429 with `Retry-After: 5` |

A slow embedding model does not cause a 503. `search` answers with `search_mode=keyword_fallback` instead. The worst case for one call is about 23 seconds (a 10-second queue wait plus the query), under this server's 30-second `DEFAULT_TIMEOUT`.

How the tools handle these: tool arguments that become `q` are capped below 512 characters (`question` 500; `keywords`, `wording`, and `facility` 200), and the brief's peer searches send cluster labels, the longest of which is 355 characters. A 429 or 503 reaches the assistant as a failed tool call, with a hint to wait and retry (429) or to narrow the question (503), not the "API not reachable" hint. Tools do not retry on their own: a retry would add another queue wait to a call that is already slow, during an overload, and the assistant can retry and tell the user why.

**`GET search`.** Requires `q`, in any wording, including a whole sentence. Takes the `recommendations` filters, `limit`, and `offset`. Every query runs keyword (BM25) and semantic (`nomic-embed-text`) search over recommendations and over corrective actions, merged by reciprocal rank fusion. Items are the `recommendations` items plus `matched_by`, the lists that found the item (`keyword:recommendation`, `semantic:recommendation`, `keyword:corrective_action`, `semantic:corrective_action`). `total` is the shortlist size, at most 100. `page_hits` holds up to 5 PDF pages on the first page of results, with `node_id`, `page_no`, `snippet`, `report_number`, `title`, `url`, `pdf_url`, and `published_at`. `search_mode` is `hybrid`, or `keyword_fallback` when the embedding model is unavailable; results are still valid, but report the fallback rather than hiding it.

**`GET /health/search`** (outside `/v1/`; needs the API key). `status` is `ok` or `degraded`, with `model_reachable`, `model_compatible`, `configured_model`, `dataset_model`, `vectors` (count by kind), `searches_since_start`, and `keyword_fallbacks_since_start`. `/health` only says the process is up, and is the one open endpoint.

**Report text is quoted material.** `text`, `corrective_action`, `snippet`, `summary`, and `title` are verbatim OIG report and PDF text, and reach the model as tool output (oig-data-source finding SR-22). The data side swept the corpus and found no patient identifiers and no zero-width characters. On this side, every tool result that carries report text names those fields in `provenance.quoted_fields`, with `provenance.quoted_text` saying they are source material and not instructions. The five tools that return report text say the same in their descriptions, and every tool is annotated read-only and has no write or shell ability.

**`GET meta`.** `counts` adds `facility_responses`, `facilities`, `inspections`, `clusters`, and `duplicate_report_listings` (`reports` counts listings, so distinct reports are `reports` minus that). `reconciliation` compares the database with the totals OIG prints on `/recommendations-all` on `checked_on`: for each of `open`, `total_recommendations`, and `total_reports`, the `database` and `oig` values, the `difference`, and `within_tolerance`, plus `oig_open_by_age`. `derived` records how the derived tables were built, including the cluster method.

**`GET recommendations`.** The exact, countable listing. Adds `status` (repeat the parameter for several values), `action_office`, `node_id`, `domain`, `has_response`, `past_target` (open, with the facility's target date already passed), and `sort` (`relevance`, `newest`, `oldest`). `sort` defaults to `relevance` when `q` is set and `newest` otherwise. An `action_office` abbreviation such as `VHA` or `EHRM IO` matches the parenthesized form; any other value matches part of the office name. One recommendation can name several offices, joined by commas in `action_office`. Each item has `rec_id`, `node_id`, `rec_no`, `text`, `action_office`, `status`, `closure_date`, `report_number`, `title`, `published_at`, `url`, `report_type`, and `response` (the same object as in report detail, or null).

**`GET reports`.** Adds `path` and `has_recommendations`. Each item has `node_id` (nullable), `path`, `report_number`, `title`, `url`, `report_type`, `published_at`, `rec_count`, `open_count`, `duplicate_of`, and `topics`. `duplicate_of` is null, or the `path` of the listing to use when OIG lists one report twice. Both listings are returned here, so `total` counts listings; `metrics/counts`, `reports_in_scope`, and facility `report_count` count such a report once.

**`GET reports/{node_id}`.** Returns the report fields plus `summary`, `pdf_url`, `monetary_impact` (`open` and `closed`, in dollars, as OIG totals them on the listing), `questioned_costs` and `better_use_of_funds` (from the report page), `facets` (facet name to labels), `standards_cited`, and `recommendations`. Each recommendation adds `response` (`domain`, `concur`, `target_date`, `target_date_precision`, `target_date_raw`, `corrective_action`, `page_no`, or null) and `status_history` (one `{observed_at, status, closure_date}` per crawl). `target_date` is `YYYY-MM-DD` at `day` precision and `YYYY-MM` at `month` precision; `target_date_raw` is the wording in the report, including values such as "Completed" that have no date. An unknown node id returns 404.

**`GET pages/search`.** Requires `q`; takes `q_mode`, `node_id`, and the report filters. Items have `node_id`, `page_no` (the physical PDF page), `snippet` (matches wrapped in `**`), `report_number`, `title`, `url`, `pdf_url`, `published_at`, and `report_type`, in BM25 order. Only reports with recommendations have PDF text; the other reports on the site are not indexed.

**`GET facilities`.** Filters are `q` (part of a name, an alias, or a linked report's title, which is how a city such as "West Haven" finds its system; or an exact station number), `visn` (number, for example `17`), and `state`. Items have `station_number`, `name`, `aliases`, `visn`, `state`, `report_count`, `recommendation_count`, and `open_count`. The registry holds facilities and regional offices named by a station number in a report's memo headers, not central-office routing symbols.

**`GET facilities/{station_number}`.** Takes `recommendations_limit` (0 to 100, default 25, newest first), because a large facility can otherwise fill an assistant's context; `recommendations_has_more` says whether more exist, and `recommendations?station_number=` pages through them. The same fields plus `reports` (each with `link_method`: `station_number` when the PDF says so, `title_match` when inferred from the title), `inspections`, `next_window_basis`, and `recommendations`, which carry report fields and the flat response fields `domain`, `concur`, `target_date`, `target_date_precision`, `corrective_action`, and `response_page_no`. `repeat_findings` lists clusters the facility was cited under in two or more of its reports (`cluster_id`, `label`, `report_count`, `first_published`, `last_published`, `status_counts`, `rec_ids`), and `repeat_findings_basis` states what that does and does not show; pass it on, since a repeat means the same issue was cited again and not that nothing was done. Each recommendation also has `cluster_id`. An unknown station returns 404.

**`GET inspections`.** Filters are `station_number`, `program` (`HFI`, `CHIP`, or `CAP`, the program before CHIP), `published_from`, `published_to`, and `latest_only`. Items have `node_id`, `path`, `station_number`, `facility_name`, `program`, `inspection_start`, `inspection_end`, `published_at`, `report_number`, `title`, `url`, `rec_count`, `is_latest`, `next_window_estimate`, `next_window_based_on`, and `next_window_is_estimate`. An inspection that made no recommendations has `node_id` null, `inspection_start` and `inspection_end` null, and `rec_count` 0, and can still be the latest. Latest goes by `published_at`. The estimate is set only on a facility's latest inspection and is the inspection end, or the publication date for a clean inspection, plus three years; `next_window_based_on` is `inspection_end` or `published_at`. **It is an estimate and must be labeled as one wherever it is shown**; `next_window_basis` in the response states why. OIG publishes no schedule.

**`GET clusters`.** Filters are `q` (wording in the label or any member), `min_reports`, `active_since` (a year), and the member filters `report_type`, `domain`, and `published_from`. Items have `cluster_id`, `label` (one member's text), `method`, `threshold`, `member_count`, `report_count`, `matching_report_count` (reports passing the member filters, which is what `min_reports` tests), `first_year`, `last_year`, `open_count`, and a closure benchmark following the same filters (`days_sample_size`, `median_days`, `q1_days`, `q3_days`, `not_implemented_rate`), ordered by `matching_report_count`. The response adds `reports_in_scope`, every report matching `report_type` and `published_from`, including those with no recommendations. `matching_report_count` over `reports_in_scope` says how common a finding is; report that rather than a bare count. Use `report_type=healthcare-facility-inspection` for findings under the current program. Clusters come from two methods, named in `method`. `normalized-prefix-1`: opening words match after the addressee, numbers, punctuation, and facility names are removed, across five or more reports. `semantic-seed-1`, for Healthcare Facility Inspection reports only, whose wording varies too much for that: recommendations similar in meaning (cosine 0.88 or more) to one central recommendation, across three or more reports; its `label` is that recommendation. A cluster suggests a shared issue; it does not prove a common cause.

**`GET clusters/{cluster_id}`.** The same fields, with the benchmark over all members, plus `status_counts` and `members`, the recommendations with status, closure date, report fields, `station_number`, and `facility_name`. An unknown cluster returns 404.

**`GET metrics/closure`.** Requires `group_by` (`office`, `topic`, or `report_type`) and takes every `recommendations` filter and `q`. Items have `group`, `group_size`, `open_count`, `closed_count`, `closed_implemented_count`, `closed_not_implemented_count`, `not_implemented_rate` (share of closed), `days_sample_size`, `closed_on_publication_day` (closed the day the report came out, presumably fixed beforehand, which can pull a small group's median to 0), `excluded_negative_days`, `median_days`, `q1_days`, `q3_days`, `open_median_age_days`, `open_oldest_age_days`, `open_over_1_year_count`, and, for promised versus actual, `with_target_date`, `closed_by_target`, `closed_after_target`, `median_days_after_target`, and `open_past_target`. Those count only recommendations with a parsed target date, so read them with `with_target_date`; a month-precision target runs to month end. **Do not present these as missed deadlines or compute an on-time rate.** A target is the facility's estimate, and a closure date appears to record when OIG closed the recommendation after reviewing evidence, which can follow the work by months. Pass along `target_basis` in the response. There is deliberately no `group_by=facility`: the server does not rate facilities. Days run from publication to closure, and a closure dated before publication is left out of the day statistics and counted in `excluded_negative_days`. A recommendation naming two offices counts for both, and a report with two topics counts for both, so group sizes can sum to more than the filtered total. Two gaps in OIG's own data should be stated when they matter: OIG tagged only about a quarter of reports with a topic, so `group_by=topic` and the `topic` filter cover only those; and about 6 percent of closed recommendations, mostly from 2013 to 2016, show no closure date on OIG's site, which is why `days_sample_size` can be smaller than `closed_count`.

**`GET metrics/counts`.** Takes the same filters. Items are years, with `year`, `report_count`, `recommendation_count`, `open_count`, `closed_implemented_count`, `closed_not_implemented_count`, and `median_days_to_closure`. `report_count` counts every matching report when only report filters are set, including reports with no recommendations; with `q`, `status`, `action_office`, or `node_id` it counts reports with a matching recommendation.

**`GET taxonomy/{facet}`.** Facets are `topic`, `state`, `visn`, `district`, `mmc`, `author_office`, `special_project`, `action_office`, and `report_type`. The response uses the list envelope plus `facet`, with every value on one page. Items have `value` and `report_count`. Report facets add `value_id`. `action_office` adds `abbreviation`, `recommendation_count`, and `open_count`. `report_type` adds `label`. An unknown facet returns 404.
